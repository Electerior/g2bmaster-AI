# 가격 API 변경 명세 — 백엔드 개발자용

**이 문서 하나만 읽고 작업할 수 있게 썼다.** 다른 문서를 열지 않아도 된다.
용어는 §1 에서 전부 정의한다.

- 대상: `g2bmaster-backend` 의 `integration/ai/AiClient` 와 그 호출자
- 영향 엔드포인트: `POST /api/price/resolve`, `POST /api/price/url` **2개뿐**
- 작성: 2026-08-07 · 상태: **제안 — §9 의 3개 항목에 답을 받아야 확정된다**

---

## 0. 30초 요약

AI 서비스의 가격 조회가 쓰던 외부 검색 서비스(**studyweb**)를 버리고
**전용 스크래퍼**로 바꾼다. 백엔드가 해야 할 일은 5가지다.

| # | 할 일 | 난이도 | 안 하면 |
|---|---|---|---|
| 1 | **가격 결과 캐시를 백엔드에 만든다** | 중 | 요청마다 외부 사이트를 긁는다. 기존엔 AI 안에 7일 캐시가 있었고 **그게 사라진다** (§6) |
| 2 | **견적 검증·선택 로직을 백엔드로 가져온다** | 상 | 우리가 후보만 주고 아무도 고르지 않는다 (§4·§9-A) |
| 3 | `g2b.ai.timeout-ms` 를 **줄인다** | 하 | 그대로 둬도 동작은 한다. 다만 장애 감지가 느려진다 (§7) |
| 4 | 응답 필드 3개 변경에 맞춰 DTO 수정 | 하 | 역직렬화 실패 또는 조용한 `null` (§3.3) |
| 5 | 새 실패 코드 3개 처리 | 하 | `INTERNAL` 로 뭉뚱그려져 원인 추적 불가 (§5) |

**1번과 2번이 진짜 작업이다.** 나머지는 한 시간짜리다.

## 1. 배경 — 30초

### studyweb 이 뭐였나

AI 저장소가 부르던 **외부 HTTP 서비스**다. 별도 프로세스로 `localhost:8787` 에 떠 있었고
세 가지를 해 줬다.

| studyweb 엔드포인트 | 하는 일 |
|---|---|
| `POST /prices` | 품목명을 주면 여러 쇼핑몰의 가격 견적을 구조화해서 반환 |
| `POST /search` | 웹 검색 |
| `POST /extract` | 임의 URL 의 페이지 본문을 (필요하면 브라우저로 렌더해서) 텍스트로 추출 |

AI 서비스는 `/prices` 를 1순위로 쓰고, 실패하면 `/search` + `/extract` 로 페이지를 긁어
**LLM 에게 본문을 읽혀 가격 숫자를 뽑았다.**

### 왜 버리나

1. **느리다.** 측정값이 소스 주석에 남아 있다 — 정적 엔진 26.2초, 동적 30.1초,
   브라우저 렌더 153.2초. 타임아웃이 60초로 잡혀 있었다.
2. **비싸다.** 가격 하나 뽑을 때마다 LLM 호출이 한 번씩 붙는다.
3. **부정확하다.** LLM 이 페이지 본문에서 숫자를 읽는 방식이라 배송비·할인전가·
   옵션가를 본가로 착각하는 일이 구조적으로 막히지 않는다.

### 무엇으로 바꾸나

[CompoPrice](https://github.com/Hong-Iron/CompoPrice) — 다나와·ITMAYA 두 사이트의
내부 API 를 직접 치는 Python 스크래퍼다. **가격이 처음부터 정수로 나온다.**
LLM 이 본문을 읽는 단계가 통째로 사라진다.

### 대가

커버리지가 좁아진다. **1차 범위는 PC 부품·노트북·서버/워크스테이션뿐이다.**
인력·용역·일반 소매(쿠팡·11번가 등)는 후순위로 확정했다 — 나중에 붙인다.

→ **범위 밖 품목은 에러가 아니라 "가격원 없음" 으로 정상 응답한다.** §5 의 `NO_PRICE_SOURCE`.

## 2. 바뀌지 않는 것 (먼저 안심할 것)

- **엔드포인트 경로·메서드 그대로.** `POST /api/price/resolve`, `POST /api/price/url`.
- **실패 응답의 공통 규약 그대로.** `{code, error, retryable, retryAfterMs?, requestId}`.
- **HTTP 200 폴백을 AI 가 만들지 않는다는 원칙 그대로.** 실패는 정직한 4xx/5xx 로 온다.
  200 폴백은 지금처럼 백엔드 컨트롤러가 `AiUnavailableException` 을 잡아 만든다.
- **`error` 필드는 사용자에게 그대로 보여줄 한국어**라는 것도 그대로다.
- 나머지 9개 AI 엔드포인트는 **아무 영향 없다.**

## 3. `POST /api/price/resolve`

### 3.1 요청

```json
{
  "itemName": "인텔 제온 6526Y",
  "deadlineMs": 8000,
  "requestId": "b3f1…"
}
```

| 필드 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `itemName` | string | ✓ | 조회할 품목명. **가공하지 말고 원문 그대로 보낼 것** (§8) |
| `deadlineMs` | int | | 이 시간 안에 답한다. 없으면 AI 기본값. 자세히는 §7 |
| `requestId` | string | | 두 저장소 로그를 잇는 값. 응답에 그대로 돌아온다 |

요청 형식은 **바뀌지 않는다.**

### 3.2 응답 200

```json
{
  "quotes": [
    {
      "source": "danawa",
      "sourceId": "103453760",
      "url": "https://prod.danawa.com/info/?pcode=103453760",
      "name": "인텔 제온 6526Y (정품)",
      "priceKrw": 4432000,
      "spec": "16코어/32스레드/2.8GHz/195W",
      "basis": "listed",
      "collectedAt": "2026-08-04T10:46:18+09:00",
      "stale": false
    }
  ],
  "searchInfo": {
    "status": "found",
    "queryUsed": "제온 6526Y",
    "relaxed": false,
    "relaxation": {
      "droppedFilters": [],
      "notes": [],
      "textFallback": []
    },
    "quoteCount": 3,
    "misses": []
  },
  "degraded": false,
  "degradedReasons": [],
  "requestId": "b3f1…"
}
```

#### `quotes[]` — 가격 후보

| 필드 | 타입 | 설명 |
|---|---|---|
| `source` | string | `"danawa"` \| `"itmaya"` \| `"index"`(로컬 색인) |
| `sourceId` | string | 사이트 내부 식별자 (다나와 `pcode`, ITMAYA `idx`) |
| `url` | string | 사람이 열어서 확인 가능한 상품 페이지 |
| `name` | string | 판매처가 표기한 상품명. **`itemName` 과 다를 수 있다** — 검증 대상이다 |
| `priceKrw` | int | 원화 정수 |
| `spec` | string | 판매처 표기 사양 문자열. 검증에 쓸 수 있다 |
| `basis` | enum | 이 가격의 성격. **아래 표 필독** |
| `collectedAt` | string | ISO-8601 KST. 이 가격을 실제로 본 시각 |
| `stale` | bool | 신선도 기준을 넘긴 값인가 |

**`basis` 는 새로 생긴 필드이고, 이걸 무시하면 안 된다:**

| `basis` | 뜻 | 백엔드가 할 일 |
|---|---|---|
| `listed` | 그 URL 에 그 가격이 실제로 표시돼 있었다 | 그대로 신뢰 가능 |
| `derived` | **환산값이다.** 용량당 단가로 스케일했거나, 2개 묶음가를 2로 나눴다 | 견적에 쓸지 정책적으로 판단. 최소한 화면에 표시할 것 |
| `stale` | 색인에서 읽었고 신선도 기준을 넘겼다 | `collectedAt` 을 함께 보여줄 것 |

`derived` 를 `listed` 처럼 다루면 **틀린 단가가 조용히 견적에 들어간다.**

#### `searchInfo` — 어떻게 찾았는가

| 필드 | 타입 | 설명 |
|---|---|---|
| `status` | enum | `"found"` \| `"not-found"` \| `"no-source"` |
| `queryUsed` | string | 실제로 검색에 쓴 문자열 |
| `relaxed` | bool | **요청한 조건을 다 지키지 못했는가.** §8 의 핵심 |
| `relaxation.droppedFilters` | string[] | 적용하지 못한 스펙 조건 (예: `"gpu_memory=24GB — 이 카테고리에 없는 속성"`) |
| `relaxation.notes` | string[] | 경로 변경 기록 (예: `"카테고리를 못 찾아 통합검색으로 대체"`) |
| `relaxation.textFallback` | string[] | 정식 필터 대신 상품명 문자열로 걸러낸 조건 |
| `quoteCount` | int | 검색이 돌려준 총 후보 수 (검증 전) |
| `misses` | object[] | 확인 실패한 가격원 `{site, reason}` |

`status = "no-source"` 는 **정상 응답이다.** 인력·용역처럼 아직 가격원이 없는 품목에서 나온다.
장애가 아니므로 재시도하지 말 것.

### 3.3 이전 응답과의 차이 — DTO 수정 지점

| 이전 (studyweb) | 이후 | 조치 |
|---|---|---|
| `result` (단일 객체, AI 가 골라서 줌) | `quotes[]` (후보 목록) | **§4 참조. 가장 큰 변경** |
| `result.provider: "studyweb"` | **삭제** | 이 문자열로 분기하는 코드가 있으면 제거 |
| `result.source: "web"` \| `"local-db"` | `quotes[].source: "danawa"` \| `"itmaya"` \| `"index"` | enum 값이 전부 바뀐다 |
| `result.basis: "page"` \| `"snippet"` \| `"local-price-db"` | `quotes[].basis: "listed"` \| `"derived"` \| `"stale"` | **enum 값이 전부 바뀐다** |
| — | `quotes[].collectedAt` | 신규 |
| — | `quotes[].stale` | 신규 |
| — | `quotes[].sourceId` | 신규 |
| `searchInfo.relaxed` (bool) | 유지 + `searchInfo.relaxation` (구조체) | 기존 bool 은 그대로 두므로 **당장 안 고쳐도 깨지지 않는다** |
| `searchInfo.rejectedQuoteCount` | 삭제 | 검증 주체가 바뀌므로 우리가 계산할 수 없다 (§4) |

`searchInfo.relaxed` 를 그대로 남긴 이유는 **§8 의 강제 규칙이 그 값 하나로 돌아가기 때문**이다.
당장은 bool 만 봐도 되고, 사용자에게 "무엇 때문에 못 찾았는지" 를 보여주고 싶을 때
`relaxation` 을 읽으면 된다.

## 4. 가장 큰 변경 — 견적 검증이 백엔드로 온다 🔴

### 무슨 얘기인가

이전에는 AI 서비스가 후보 견적을 모아 **직접 검증하고 최저가 하나를 골라** `result` 로 줬다.
검증 로직은 이런 것이다.

> `"SSD 2TB"` 를 요청했는데 후보에 500GB 짜리가 섞여 있다. 최저가 규칙만 쓰면
> 가장 싼 500GB 가 단가가 된다. 그래서 요청한 사양과 후보 상품명을 대조해
> 맞지 않는 것을 버린 뒤에 최저가를 고른다.

이 판정 함수들(`deriveProductIdentity`, `quoteMatchesIdentity`)은
**분리 계약상 백엔드 소유다.** 순수 규칙 기반이고 AI 가 아니며,
`ai.enabled=false` 에서도 동작해야 하기 때문이다.

### 왜 지금 얘기하나

studyweb 시절엔 이 함수들이 AI 쪽 코드에 남아 있어서 문제가 드러나지 않았다.
가격 경로를 새로 만드는 지금이 계약대로 옮길 시점이다.

**AI 가 자기 응답을 자기가 검증하면 그건 검증이 아니다.** 문서 인용(`evidence.quote`)에
대해 이미 같은 원칙을 쓰고 있다 — AI 는 제안하고, 백엔드가 원문 대조로 채택을 판정한다.
가격도 같다.

### 그래서 백엔드가 구현할 것

```
quotes[] 수신
  → 1. itemName 에서 요구 사양 추출 (모델코드 / 용량 / 세대 …)
  → 2. 각 quote 의 name·spec 과 대조, 불일치 제거
  → 3. 남은 것 중 최저가 선택
  → 4. §8 의 강제 규칙 적용
  → 5. 단가 확정
```

**이건 새로 짜는 게 아니라 옮기는 것이다.** 기존 Node 구현이
`../g2bmastersopen/price-web.js` 의 `pricesToResult()` 에 있고, 검증 규칙의 근거가
주석으로 상세히 남아 있다. 그대로 포팅하면 된다.

> **이 항목은 §9-A 에서 답을 받아야 한다.** 부담이 크면 우리가 `result` 를
> 지금처럼 미리 골라 주는 방식(옵션 B)도 가능하다. 다만 계약과 어긋나고,
> `ai.enabled=false` 일 때 가격 검증이 통째로 죽는다.

## 5. 실패 코드

### 5.1 응답 본문 (기존과 동일)

```json
{
  "code": "PRICE_SOURCE_BROKEN",
  "error": "가격 정보를 가져오지 못했습니다.",
  "retryable": true,
  "retryAfterMs": 30000,
  "requestId": "b3f1…"
}
```

**HTTP status 가 아니라 `code` 와 `retryable` 로 판단할 것.**
status 는 프록시·모니터링이 읽는 값이고, 분류의 진실은 본문에 있다.

### 5.2 새로 생기는 코드 3개

| code | status | retryable | 언제 | 백엔드가 할 일 |
|---|---|---|---|---|
| `PRICE_SOURCE_BROKEN` | 502 | ✓ | 가격 사이트 응답은 왔는데 **파싱이 깨졌다** (사이트 개편 등) | 200 폴백 + 재시도. **반복되면 알림을 띄울 것 — 사람이 고쳐야 한다** |
| `UNSUPPORTED_SOURCE` | 400 | ✗ | `/api/price/url` 에 지원하지 않는 도메인의 URL 이 왔다 | 재시도 금지. 사용자에게 지원 사이트를 안내 |
| `NO_PRICE_SOURCE` | — | — | **에러가 아니다.** 200 + `searchInfo.status = "no-source"` | 재시도 금지. "이 품목은 자동 조회 대상이 아닙니다" |

`NO_PRICE_SOURCE` 를 표에 같이 적은 이유는 **에러로 착각하기 쉬워서**다.
인력·용역 품목은 이 경로를 상시로 탄다. 500 으로 만들면 안 된다.

### 5.3 `PRICE_SOURCE_BROKEN` 을 따로 둔 이유

"검색은 됐는데 결과가 0건" 과 "파서가 깨져서 0건" 은 완전히 다른 사건이다.
전자는 정상(그 물건이 시장에 없다), 후자는 **모든 품목이 동시에 조용히 실패하는 장애**다.
둘을 구분하지 않으면 사이트 개편 날 아무도 모른 채 견적이 전부 빈다.

### 5.4 기존 코드는 그대로

`BAD_REQUEST`(400) · `UNAUTHORIZED`(401) · `NOT_PORTED`(501) · `LLM_TIMEOUT`(504) ·
`INTERNAL`(500) 은 지금 쓰는 그대로다.

## 6. 캐시 — 백엔드가 반드시 만들어야 한다 🔴

### 사라지는 것

기존 Node 구현에는 **인프로세스 캐시가 있었다.**

```
성공 → 7일 보관
실패 → 60초 보관
```

새 AI 서비스는 **내구 상태를 갖지 않는다.** 큐·이력·캐시는 전부 백엔드 소유이고,
AI 프로세스가 죽어서 잃는 것은 "진행 중이던 요청 하나" 여야 한다는 것이 설계 원칙이다.

### 그래서 무슨 일이 생기나

**캐시를 안 만들면 같은 품목을 100번 조회하면 외부 사이트를 100번 긁는다.**
기존엔 7일에 한 번이었다. 이건 성능 문제가 아니라 **차단당하는 문제**다.

### 권장 정책

| 항목 | 값 | 근거 |
|---|---|---|
| 성공 결과 TTL | **7일** | 기존 동작과 같게. 부품 가격은 주 단위로 움직인다 |
| 실패 결과 TTL | **60초** | 기존 동작과 같게. 일시 장애를 오래 물고 있지 않는다 |
| `no-source` TTL | **길게 (1일+)** | 범위 밖 품목은 내일도 범위 밖이다 |
| 캐시 키 | `itemName` 정규화값 | 아래 주의 |
| `degraded: true` 인 응답 | **캐시하지 않는다** | 불완전한 결과가 눌러앉는다 |

**주의 — 캐시 키에 프롬프트 버전을 넣지 말 것.** 다른 AI 엔드포인트의 재사용 키에는
`GET /api/ai/prompt-version` 값이 들어가지만, **가격 조회에는 LLM 이 관여하지 않으므로
프롬프트 버전과 무관하다.** 넣으면 프롬프트를 고칠 때마다 가격 캐시가 통째로 버려진다.

---

## 7. 타임아웃 재설정

### 지켜야 할 부등식

```
AI 자체 데드라인  <  g2b.ai.timeout-ms  <  백엔드 리스 시간
```

이게 깨지면 백엔드가 우리를 포기한 뒤에도 우리는 계속 긁고 있고,
다른 워커가 같은 작업을 다시 집는다. 같은 일을 두 번 한다.

### 값이 이렇게 바뀐다

| | 이전 (studyweb) | 이후 (CompoPrice) |
|---|---|---|
| 실제 소요 | 26 ~ 153초 | **2 ~ 5초** |
| AI 내부 타임아웃 | 60초 | 8초 제안 |
| `g2b.ai.timeout-ms` (가격) | 그보다 큰 값 | **10초 제안** |

가격 조회는 이제 다른 AI 엔드포인트보다 훨씬 빠르다.
`g2b.ai.timeout-ms` 가 **모든 AI 호출에 공용이라면 가격만 따로 짧게 두는 것이 낫다** —
공용값을 10초로 내리면 심층 분석이 죽는다. 별도 설정이 어려우면 그냥 두어도 동작은 한다
(장애 감지가 느려질 뿐이다).

`deadlineMs` 를 요청에 실어 주면 우리가 그 안에서 페이지 수를 역산해 맞춘다.

## 8. 그대로 유지해야 하는 규칙 — "완화 검색이면 단가로 쓰지 않는다"

기존 계약에 이 규칙이 있고, **반드시 유지된다.**

> 규격 문구를 모델명으로 해석했는데, 그 모델명으로 못 찾아 검색어를 깎았다면
> `result` 를 강제로 `null` 로 만든다.

실제 사고 사례가 있다 — `"GPU 메모리 24GB 이상"` 이 `Arc Pro B60` 으로 해석됐고,
그걸로 못 찾자 `"B60"` 으로 완화돼 **15,000원짜리 엉뚱한 물건**을 물어왔다.
틀린 단가는 없는 단가보다 나쁘다. 사람이 고칠 기회조차 사라진다.

### 판정 조건 (변경 없음)

```
if (규격→모델 해석이 일어남  &&  결과가 있음  &&  searchInfo.relaxed == true)
    result = null
```

### 달라지는 것 — 이유를 설명할 수 있게 된다

이전에는 "완화됐다" 는 사실만 알았다. 이제 `searchInfo.relaxation.droppedFilters` 에
**무엇을 못 지켰는지가 문자열로 들어온다.** 사용자에게 이렇게 보여줄 수 있다.

> `'RTX 5090 32GB'` 로는 못 찾아 `'RTX 5090'` 으로 완화 검색됐습니다.
> **못 지킨 조건: GPU 메모리 32GB** — 다른 제품일 수 있어 단가로 쓰지 않습니다.

**이 규칙은 백엔드 소유다.** AI 는 `relaxed` 와 `relaxation` 을 보고할 뿐,
`result` 를 `null` 로 만들지 않는다.

## 9. 답을 받아야 하는 것 3개

이 세 가지가 정해지기 전엔 우리가 구현을 시작할 수 없다.

### A. 견적 검증을 백엔드가 가져갈 것인가 (§4)

| 옵션 | 내용 | 우리 의견 |
|---|---|---|
| **A-1** | 백엔드가 `quotes[]` 를 받아 검증·선택 | **권장.** 계약과 일치. `ai.enabled=false` 에서도 가격 검증이 산다 |
| A-2 | 지금처럼 AI 가 `result` 하나로 골라 줌 | 백엔드 작업은 줄지만, AI 가 자기 응답을 자기가 검증하게 된다 |

### B. `POST /api/price/url` 을 어떻게 할 것인가

studyweb 의 `/extract`(임의 URL 본문 추출) 를 대체할 수단이 **없다.**

| 옵션 | 내용 | 우리 의견 |
|---|---|---|
| **B-1** | 다나와·ITMAYA 상품 URL 만 지원. 나머지는 `UNSUPPORTED_SOURCE` | **권장.** 파서를 이미 갖고 있고, 외부 URL 을 받아 fetch 하는 보안 표면이 화이트리스트로 줄어든다 |
| B-2 | 임의 URL 을 우리가 받아 파싱 | 어떤 쇼핑몰이든 정확히 파싱한다는 보장이 없다. SSRF 방어 부담도 진다 |
| B-3 | 이 엔드포인트를 없앤다 | **프론트에 이 기능이 실제로 쓰이는지 백엔드만 안다** — 판단해 줄 것 |

### C. `g2b.ai.timeout-ms` 를 엔드포인트별로 나눌 수 있는가 (§7)

가격만 10초로 두고 싶다. 공용 설정 하나뿐이면 그냥 두겠다.

## 10. 배포 순서

깨지지 않게 넣는 순서다.

```
1. [백엔드] 캐시 구현 (§6)                    — 먼저. 없으면 2번부터 사이트를 과하게 긁는다
2. [백엔드] 새 실패 코드 3개 처리 (§5)         — 응답 본문의 code 를 읽는 코드가 필요
3. [AI]     /api/price/resolve 구현·배포       — 이 시점까지 501 을 반환하므로 안전
4. [백엔드] quotes[] 검증·선택 구현 (§4)       — A-1 을 택한 경우
5. [백엔드] 타임아웃 조정 (§7)                 — 마지막. 안정화 후
```

**3번 이전까지 이 엔드포인트는 `501 NOT_PORTED` 를 반환한다.**
`AiClient` 가 이미 그걸 `AiUnavailableException` 으로 바꿔 200 폴백을 만들고 있으므로,
1·2번을 먼저 넣어도 아무것도 깨지지 않는다.
