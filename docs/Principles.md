# 원칙 — g2bmaster-AI

이 문서는 **AI 저장소에서 반복적으로 내려야 하는 판단의 기준**을 적어 둔 것이다.
개별 계약은 백엔드 쪽 문서가 갖는다:

- 프론트↔백엔드 라우트 계약 → `g2bmaster-backend/docs/api-contract.md`
- 저장소 분할 경계와 합의 항목 → `g2bmaster-backend/docs/ai-boundary.md`

여기서 정하는 것은 **그 계약을 어떻게 지킬 것인가**이다.
계약과 원칙이 충돌하면 계약이 이긴다. 대신 그 충돌은 기록하고 백엔드에 역제안한다(§7.3).

---

## 1. 경계

### 1.1 우리는 추론만 소유한다

`ai-boundary.md` §1의 뒤집힌 문장이다. 백엔드가 추론하지 않는 대신,
**우리는 내구 상태를 갖지 않는다.** 작업 큐, 리스, 재시도 장부, 결과 이력,
임베딩 저장, 내보내기 상태는 전부 백엔드 소유다.

판단이 애매하면 이렇게 물어라 — *"이 데이터를 잃으면 사용자가 뭔가를 다시 해야 하는가?"*
그렇다면 우리 것이 아니다.

### 1.2 프로세스는 언제든 죽어도 된다

위의 따름정리다. 재시작으로 잃는 것이 진행 중이던 요청 하나뿐이어야 한다.
로컬 디스크·프로세스 메모리에 결과를 쌓는 설계는 금지한다.
캐시를 두더라도 **소실 시 비용만 증가하고 정합성은 깨지지 않는** 종류여야 한다.

### 1.3 두 개의 계약을 혼동하지 않는다

프론트가 보는 계약과 백엔드가 우리에게 거는 계약은 다르다.
`api-contract.md`의 라우트 이름·응답 봉투·한국어 오류 문구는 **백엔드가 지키는 것**이고,
우리가 지키는 것은 `ai-boundary.md` §5의 11개 엔드포인트다.

특히 **HTTP 200 폴백 계약은 우리 것이 아니다**(§2.1 참조).

## 2. 정직성

가장 자주 어기게 되는 원칙이고, 어겼을 때 가장 늦게 발견된다.

### 2.1 실패를 성공으로 포장하지 않는다

`ai-boundary.md` §6.4의 200 폴백은 **백엔드 컨트롤러가 `AiUnavailableException`을 잡아
만드는 것**이다. 우리가 미리 200으로 포장하면 백엔드는 실패를 구분할 근거를 잃는다.
그러면 §6.3의 "폴백을 성공으로 치지 않는다"가 집행 불가능해지고,
**폴백 결과가 캐시에 눌러앉아 영원히 재분석되지 않는다.**

→ AI→백엔드 구간에서 실패는 정직한 4xx/5xx로 내린다. 분류표는 `docs/failure-modes.md`.

### 2.2 부분 성공은 부분 성공이라고 말한다

법령 검토는 됐는데 요약이 실패한 경우처럼 스텝별로 갈리는 상황이 정상이다.
이때는 200 + `degraded: true` + `degradedReasons[]` 로 반환한다.
`degraded`는 백엔드에게 **"쓰되 캐시하지 말고 재시도 대상으로 둬라"** 는 신호다.
값이 있다는 이유로 `degraded`를 생략하지 않는다.

### 2.3 완화·추정·불확실을 숨기지 않는다

> 틀린 단가는 없는 단가보다 나쁘다. (`api-contract.md` §F)

가격 경로에서 규격→모델 해석이 일어났는데 검색이 질의를 완화했다면
`queryRelaxed: true`를 반드시 실어 보낸다. `result`를 `null`로 만드는 최종 강제는
백엔드가 하지만, **완화 사실을 숨기면 백엔드는 그 규칙을 집행할 방법이 없다.**

같은 원리가 다른 곳에도 적용된다 — 컨텍스트가 잘렸으면 잘렸다고,
첨부를 못 읽었으면 못 읽었다고, 모델이 폴백 모델이었으면 그렇다고 응답에 남긴다.

### 2.4 검증받을 수 있는 형태로 반환한다

`ai-boundary.md` §4가 근거 인용 검증을 백엔드에 둔 이유는 명시적이다 —
*AI 응답을 검증하는 쪽이 AI 자신이면 검증이 아니다.*

우리는 그 검증을 회피하지 않고 **검증하기 쉽게 만든다.**

- 인용은 `{documentId, quote, offset, length}` 로 반환한다. 문자열만 주면
  같은 문구가 여러 번 나올 때 대조가 모호해진다.
- 반환 직전 우리 쪽에서도 축자 일치를 확인하고, 불일치 인용은 버린다.
  백엔드에서 기각당하면 원인이 보이지 않는다.

## 3. 결정성과 재현성

### 3.1 출력 의미를 바꾸는 모든 것은 버전이다

프롬프트 버전은 분석 결과 재사용 키의 일부다(`ai-boundary.md` §6.1).
따라서 버전을 올려야 하는 것은 프롬프트 문구만이 아니다:

- 프롬프트 텍스트
- 모델 ID
- 디코딩 파라미터(temperature, top_p 등)
- 후처리·파싱 규칙
- 청킹·클램프 방식

**손으로 문자열을 고치는 방식은 반드시 잊어버린다.**
버전은 `프롬프트 해시 + 모델 ID + 디코딩 파라미터 해시`로 자동 파생하고,
사람이 읽을 라벨(`item-summary-2026-08-04-v4`)은 접두사로만 둔다.
버전이 안 올라가면 백엔드가 낡은 결과를 계속 재사용하고, 우리는 "고쳤는데 안 바뀐다"로
며칠을 잃는다.

### 3.2 LLM이 닿는 표면을 최소화한다

클램프 산술, 파일명 복원, 품목 정규화, 응답 파싱, 인용 대조는 전부 **순수 함수**다.
LLM 호출과 섞지 않는다. 이렇게 나눠야 테스트의 90%가 모델 없이 돌고,
장애 원인이 "모델이 이상함"과 "우리 코드가 이상함"으로 갈린다.

### 3.3 텍스트 좌표계를 훼손하지 않는다

프롬프트에 넣기 전 정규화(공백 정리, 표 평탄화, 유니코드 정규화, 머리글 제거)를 하면
LLM은 정규화본을 인용하고 백엔드는 원본과 대조한다. **인용이 전부 기각된다.**

원본 문자열을 진실로 두고, 정규화가 필요하면 원본 offset으로 되돌릴 수 있는
매핑을 유지한다. 되돌릴 수 없는 변형은 하지 않는다.

### 3.4 임베딩은 벡터와 버전을 함께 반환한다

벡터는 백엔드 DB에 저장되고 유사도 계산도 백엔드가 한다(`ai-boundary.md` §4).
모델이 바뀌면 **기존 벡터와의 코사인 비교 자체가 무의미해진다.**
`embeddingVersion`·`model`·`dim`을 항상 함께 내려보내고, 백엔드가 같이 저장하게 한다.
`analysisInputHash` 고아 문제(§6.2)와 정확히 같은 종류의 사고다.

### 3.5 클램프는 상수가 아니라 계산식을 이식한다

`SPEC_MAX_CHARS = 50000`, 문자/토큰 1.8, 프롬프트 여유 1500 토큰.
상수만 옮기고 산술을 새로 짜면 경계에서 조용히 다르게 동작한다.
원본과 동일 입력에 동일 출력을 내는 골든 테스트를 먼저 만든다.

## 4. 시간과 자원

### 4.1 데드라인은 호출자가 준다

`g2b.ai.timeout-ms` 하나로 embed와 심층 분석을 함께 덮을 수 없다.
요청 본문의 `deadlineMs`를 받아 **스텝마다 잔여 시간을 확인**하고,
초과하기 전에 부분 결과 또는 실패를 반환한다.

### 4.2 백엔드 리스보다 먼저 끝난다

백엔드 워커는 `claim → heartbeat → execute → complete`로 돈다.
우리가 리스 시간을 넘기면 **다른 워커가 같은 작업을 다시 집고, 우리는 여전히 추론 중**이다.
LLM 비용이 두 배로 나가고 결과는 하나만 채택된다.
`AI 자체 데드라인 < timeout-ms < 리스 시간` 부등식을 항상 성립시킨다.

### 4.3 상한은 스스로 건다

동시 LLM 호출 수, 요청당 토큰 예산, 첨부 처리량에 서비스 자체 상한을 둔다.
검색 팬아웃이 수십 건을 한꺼번에 밀어넣을 수 있고, 우리 쪽에 상한이 없으면
워커 풀이 아니라 우리가 먼저 무너진다.

### 4.4 재시도는 한 겹만 둔다

백엔드에 이미 재시도가 있다(`analysis-job-queue.js`).
우리 안에서 재시도할 것은 **같은 요청 안에서 값싸게 회복 가능한 것**뿐이다 —
LLM 응답 JSON 파싱 실패, 엔드포인트 페일오버 정도. 그 이상은 실패로 올린다.
두 겹 재시도는 백엔드가 계산하는 ETA와 비용 예측을 전부 무너뜨린다.

## 5. 파이프라인

### 5.1 스텝은 객체다

`item-summary`의 6단계(재사용 캐시 → 첨부 → 컨텍스트 클램프 → 사실 추출 → 본 요약 →
품목 추출)는 각각 `(입력, 컨텍스트) → 결과 | 폴백사유`를 반환하는 스텝으로 만든다.
함수 호출로 이어 붙이면 중간 실패 시 **어디까지 성공했는지 말할 수 없고**,
§2.2의 `degradedReasons`를 채울 수 없다.

### 5.2 `sourceTrace`는 부산물이 아니라 산출물이다

무엇을 읽었고, 무엇을 못 읽었고, 무엇을 잘랐는지가 응답에 남아야 한다.
사용자가 판단을 이어가는 근거이고, 우리가 사후에 품질을 조사할 유일한 단서다.

### 5.3 LLM 호출은 단일 어댑터를 통과한다

모델 교체 때문이 아니라 **토큰·비용·지연·프롬프트 버전·재시도 정책을 한 곳에서
관측하기 위해서**다. 어댑터를 우회하는 호출이 하나라도 생기면 §3.1의 버전 자동 파생이
거짓말이 된다.

### 5.4 프롬프트는 코드가 아니라 자산이다

레지스트리에 ID로 등록하고, 변경은 버전 파생을 거친다.
`POST /api/bid-summary`와 `GET` 버전의 프롬프트가 다른 것은 **계약이다**
(`api-contract.md` §D). 리팩터링하면서 하나로 합치지 않는다.

## 6. 테스트

1. **LLM 없이 도는 테스트가 기본이다.** 순수 함수 골든 테스트가 주력이고,
   실제 모델 호출은 소규모 평가셋과 기록/재생으로 제한한다. 매 CI마다 호출하지 않는다.
2. **실패 주입이 정상 경로만큼 중요하다.** 타임아웃, 잘린 JSON, 엔드포인트 전멸,
   데드라인 초과를 주입해 §2.1의 분류표대로 나가는지 확인한다.
   이것이 폴백 계약의 유일한 자동 검증 수단이다.
3. **응답 스키마는 스냅샷으로 고정한다.** 필드 하나가 백엔드 파싱을 깨뜨린다.

## 7. 계약을 다룰 때

### 7.1 필드 추가는 자유, 제거와 의미 변경은 합의

추가는 백엔드가 무시하면 그만이다. 제거·이름 변경·의미 변경은 두 저장소를 동시에 깬다.

### 7.2 한국어 문구는 사용자 대상 계약이다

`aiError`에 넣는 사유는 그대로 화면에 렌더링된다(`api-contract.md` §1.1).
상수로 모으고, 코드에서 문자열을 조립하지 않는다. 내부 원인은 `code`로 따로 보낸다.

### 7.3 합의가 필요해지면 문서에 되돌린다

작업 중 "이건 백엔드와 정해야 한다"가 나오면 구현으로 우회하지 말고
`ai-boundary.md` §6의 합의 목록에 추가하자고 제안한다.
현재 §6은 네 항목이지만 최소한 다음이 더 필요하다:

- `embeddingVersion`의 저장 여부 (§3.4)
- 엔드포인트별 타임아웃과 리스 시간의 부등식 (§4.2)
- 인용 좌표계 — 문자열 대조인가 offset 대조인가 (§2.4)
- `_analysisHistoryId`의 생성 주체 — 이력을 소유한 쪽이 만드는 것이 맞다
- `prompt-version`을 엔드포인트별 맵으로 확장할지 (§3.1)

## 8. 이 원칙을 어겨야 할 때

원칙은 기본값이지 금지 규정이 아니다. 어겨야 할 이유가 있으면 어기되,
**무엇을 왜 어겼는지 코드 주석과 결정 기록에 남긴다.**

`api-contract.md` §4가 좋은 예다. 거기 적힌 열 가지는 전부 과거 장애의 흔적이고,
이유가 함께 적혀 있었기 때문에 이식할 때 살아남았다.
이유 없는 규칙은 다음 사람이 정리해 버린다.
