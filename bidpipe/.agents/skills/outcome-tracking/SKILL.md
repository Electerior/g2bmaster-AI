# 개찰결과 회수 루프 (사후 대조)

## 왜 필요한가

파이프라인이 **분석 → 투찰 → 끝**으로 열려 있어서 결과가 안 돌아온다.
그래서 우리가 산정한 원가·마진율이 맞았는지 아무도 모르고, 가격 DB의 신뢰도를
"URL을 남겼다" 수준의 절차 준수로만 주장하게 된다.

개찰결과를 회수하면 신뢰도가 **숫자**가 된다.
- 낙찰가 대비 우리 원가 비율 → 우리 소싱이 시장 대비 어느 위치인가
- 우리 투찰가 < 실제 낙찰가였나 → 실제로 먹을 수 있었던 건인가
- 전 참여업체 투찰금액 → **경쟁사 원가 역산**
- 우리가 적은 기초금액 vs 실제 예정가격 → 공고 파싱 정확도

## 데이터

- 로그: `.agents/data/outcomes/outcomes.jsonl` — **append-only**. 절대 덮어쓰지 않는다.
  재수집하면 새 줄을 추가하고, 조회 시 `collected_at` 최신 줄을 쓴다.
- 스크립트: `.agents/scripts/outcome_tracker.py`

```
python .agents/scripts/outcome_tracker.py pending        # 개찰 지난 미수집 건
python .agents/scripts/outcome_tracker.py pending --all  # 전체 추적 목록(개찰전 포함)
python .agents/scripts/outcome_tracker.py merge in.json  # 수집 결과 append
python .agents/scripts/outcome_tracker.py report         # 오차 리포트
```

`pending`은 날짜 단위 판정이라 개찰 당일 오전에는 아직 결과가 없을 수 있다.
수집기가 `status:"pending"`을 돌려주면 정상이고, 다음 회차에 다시 시도하면 된다.

### outcomes.jsonl 한 줄 스키마

```json
{"bid_no":"R26BK01687990","status":"개찰완료","ref_no":"P812026007CC",
 "opened_at":"2026/08/20 09:07:23","title":"…","org":"…","demand_org":"…",
 "est_price":333786600,"base_price":null,
 "bidders":[{"rank":1,"bizno":"367-81-02841","company":"태영솔루텍 주식회사","ceo":"박정우",
             "amount":333780000,"rate":99.998,"qty":null,"lot":null,
             "bid_at":"2026/08/19 15:07:00","memo":"정상"}],
 "win_amount":333780000,"win_company":"…","n_bidders":1,
 "collected_at":"2026-08-20T09:13:55","source":"g2b-개찰결과"}
```

`win_amount`/`win_company`/`n_bidders`는 `merge`가 bidders에서 자동 채운다.
`status`는 화면의 진행상태 그대로: `개찰완료` / `유찰` / `취소` / `pending`.

## 나라장터 수집 경로 (2026-08-20 검증, 비로그인 가능)

`www.g2b.go.kr` → 상단 **입찰** → **입찰개찰/낙찰** → **개찰결과분류조회**

- 첫 진입 시 공지 팝업 2개를 먼저 닫는다.
- URL이 SPA(`?bodyDataKey=…`)라 **직접 URL 구성이 안 된다.** 메뉴를 타야 한다.
- **입찰공고번호를 채우면 개찰일자 범위 입력이 자동 비활성화된다 = 기간 제한 없이 조회된다.**
  차수(`-000`)는 빼고 넣는다.
- 결과 행이 없으면(`데이터가 없음`) 아직 개찰 전이다. 오류가 아니다.
- 행 끝의 진행상태(`개찰완료`/`유찰`)가 **버튼**이고, 이걸 눌러야 상세로 간다.
- 상세의 라벨 옆 값은 전부 `<input>` 안에 있어 `innerText`가 빈 문자열이다.
  반드시 `input.title`로 찾아 `.value`를 읽는다.
- 투찰 그리드는 업무구분별로 분리돼 있다:
  `grdGods`(물품) / `grdSrvc`(용역) / `grdCstn`(공사) / `grdLase` / `grdRsrv`.
  행이 들어있는 그리드를 찾아 **헤더명으로 컬럼을 매핑**할 것 (물품은 `입찰금액(원)`,
  용역은 `투찰금액(원)`으로 헤더가 다르다).
- 예정가격은 `복수예비가격 및 예정가격`의 **보기** 버튼 → 팝업의 `예정가격` 필드.
- 다음 공고를 조회하려면 **목록** 버튼으로 반드시 복귀한다.
- 비로그인 시 담당자명은 `김**`로 비식별 처리된다(업체명·투찰금액은 전부 공개).

수집 코드는 `references/collector.js`를 REPL에 붙여넣어 쓴다.

## 개찰결과가 원리적으로 안 잡히는 경우: 직찰(현장입찰)

나라장터 상세의 입찰방식이 **"직찰"**이면 개찰이 발주기관 현장에서 이뤄져 개찰결과가
나라장터에 등록되지 않는다. `pending`이 아니라 **영구 미수집**이므로 추적 목록에서
별도 표시해야 한다(반복 조회 낭비).

식별 신호:
- 구버전 공고번호(숫자형): 상태가 `유찰`인데 사유가 "직찰로 진행함" / "수요기관 직찰로 진행"
- R-번호 신버전: 개찰결과분류조회에서 `데이터가 없음`이 계속 유지 (개찰일이 지났는데도)
- 공고문에 현장 입찰등록 시각·입찰실 주소가 적혀 있음

검증 사례(2026-08-20): 대구대학교 기계기구 단가구매 20230731033·20240802497(유찰+직찰 사유),
R25BK01003491·R25BK01014865(데이터 없음) — 3개년 낙찰자·낙찰가 전부 미공개.
대구대는 다른 공고(성과관리시스템 등)도 개찰결과분류조회에 안 잡혀, 기관 단위로 누락된다.

대체 경로: 기관 자체 전자입찰 시스템의 **낙찰공고 게시판**. 다만 대구대의 경우 게시되는 건
소액견적뿐이라 대형 단가계약 낙찰자는 여전히 안 나온다 → `bid-discovery`의
"기존 납품업체 확인법"으로 품목별 점유율 추정으로 대체한다.

## 나라장터 밖 공고

`outcome_tracker.py`가 공고번호 형식으로 경로를 자동 분류한다.

| 경로 | 번호 형식 | 개찰결과 확인처 | 상태 |
|---|---|---|---|
| `g2b` | `R26BK…` | 개찰결과분류조회 | 자동 수집 |
| `keti` | `Q2026…` | keti.bidsign.co.kr 낙찰자 공고 | **미구축** |
| `d2b` | `HCF…`/`LHK…` | d2b.go.kr 개찰결과 | **미구축** |

keti/d2b는 아직 수동이다. 해당 건을 수집하면 이 표를 갱신할 것.

## 지표 읽는 법

`report`가 내는 값:

- **원가/낙찰가 (%)** — 100% 초과면 그 가격에 우리는 못 맞춘다는 뜻이다.
  이 값의 **중앙값이 원가추정 신뢰도의 핵심 지표**다.
  단, 낙찰가는 경쟁사 마진이 포함된 값이므로 100% 미만이 정상이고,
  115% 이상이 반복되면 소싱 경로 자체를 의심해야 한다.
- **낙찰시 마진** — 실제 낙찰가로 수주했다면 남았을 금액.
- **would_win** — 우리 투찰가가 실제 낙찰가보다 낮았는지 (사후 시뮬레이션).
- **기초금액 오차 (%)** — 우리가 워크북에 적은 기초금액 vs 실제 예정가격.
  이건 가격조사가 아니라 **공고 파싱 정확도** 지표다.

품목군별로 오차가 쏠리면(예: RAM 다량 공고만 원가 과대) 그건 `price-research`의
해당 카테고리 조사 방법을 고쳐야 한다는 신호다. 발견 시 그 스킬에 기록한다.
